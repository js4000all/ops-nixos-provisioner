# Provisioning Roadmap

最終更新: 2026-11-08

## 現在地

管理ノード `c0` はNixOS Flakes + diskoで初期構築でき、ワーカーノードはc0上のPixiecore・nginxからUbuntu Server 26.04.1のAutoinstallを実行できる。ホスト名だけc0で指定し、対象PCのBoot Menuから一度だけPXE起動すると、ディスク初期化から自動再起動まで無人で完走することを実機で確認済み。SSH公開鍵、パスワードなしsudo、rootログイン禁止、mDNS、NTP、WoLも実機確認済み。

設定は単一のGitリポジトリに集約されている。ただし **c0はNixOSによる継続的な宣言的構成管理**、**Ubuntuワーカーは主に初回インストール時の構成管理**という違いがある。ワーカーへの後日変更は自動反映されない。

手順: [Getting Started](getting-started.md)。c0固有設定の扱い: [Local Host Config](local-host-config.md)。

## 設計原則

- 単一リポジトリで、c0構成、PXE配信基盤、ワーカー初期設定を変更管理する。
- ディスク初期化は明示的なプロビジョニング開始後のみ実施し、PXE起動しない通常の再起動で再インストールされない運用を維持する。
- OS・ISO等のバージョンとSHA256を固定し、更新は明示操作とする。
- 複数PCの同時構築は当面対象外。c0で1セッションずつ扱う。
- CLIとsystemdが制御を担い、Web UIは参照専用にする。
- まず現在の実機成功パスを維持し、機能追加と構造整理を別PRに分ける。

## マイルストーン

### M1: リポジトリ整理と最低限のテスト（優先度: 高）

責務を `controller/`（c0のNixOS/disko/install.sh）、`provisioner/`（ISO/nginx/Pixiecore/CLI）、`worker/`（Autoinstall、共通設定、役割別設定）に分けることを検討する。公開鍵など共有データは独立させる。具体的なディレクトリ名はリファクタリングPRで確定する。

- 共通設定とワーカーの役割別設定（`common` / `roles`）の境界を定義する。役割が実在するまでは抽象化を増やしすぎない。
- ISOのファイル名、URL、ハッシュ、起動用ファイルの対応を一か所で定義する。
- `flake check` / Nix評価、ShellCheck、生成されたNoCloud YAMLの構文・Autoinstallスキーマ検証をCIで実施する。
- パス移動に伴う `flake` の参照、`install.sh`、相対パス、ドキュメントを更新し、c0のdry-buildとPXE動作を再確認する。

**完了条件:** 管理ノードとワーカー双方の現在の構築手順が引き続き機能し、最低限の静的・生成物テストが自動実行される。

### M2: シンプルなプロビジョニングCLIと状態保存（優先度: 高）

現状の `ubuntu-iso-fetch.service`、`ubuntu-pxe-prepare.service`、`ubuntu-autoinstall-select`、`ubuntu-pxe.service` を統合的に操作する薄いCLIを整備する。

想定例（**未実装**）:

```sh
provision iso fetch
provision iso verify
provision prepare
sudo provision start k2
provision status
sudo provision stop
```

- ISOの有無・検証結果、起動用ファイルの状態、Pixiecoreの稼働状態、選択中のホスト名を参照できるようにする。
- 既存セッションがある場合の二重起動・ホスト切替を防ぐ。
- 実行時のGitリビジョン、OS/ISOバージョン、ホスト名、開始時刻、失敗理由を保存する。
- 再実行、部分失敗、停止時の扱いを定義する。状態ファイルかSQLiteかは必要な並行性・履歴件数を見て選ぶ。

**完了条件:** 初期準備と1台ずつのインストール操作が少数のCLIコマンドで一貫して行える。

### M3: 完了検知とセッション後片付け（優先度: 高）

- NoCloudシード取得、ISO配信、インストーラーの完了通知、再起動後のSSH到達を区別する。HTTPアクセスだけでは成功と判定しない。
- 完了通知の方式（Subiquity reporting / late-commands、または初回起動後の通知）を検討する。
- インストール完了と「運用可能（SSH、mDNS、時刻同期、必要サービス）」を別状態として記録する。
- 成功時にPixiecore停止・NoCloudシード削除。失敗時やタイムアウト時の処理を定義し、ログは保持する。
- 電源断やc0の再起動時に不整合状態を放置しないよう、再開・回復手順を整備する。

**完了条件:** 1台の処理が成功・失敗を含めて追跡可能で、成功後にPXE待受と配信シードが残らない。

### M4: 参照専用Web UI（優先度: 中）

M2/M3で確立した状態・履歴の読み取り専用ビューを作る。

- ISOファイルとハッシュ検証、PXEサーバーの稼働、現在のセッションを表示する。
- ノードごとのホスト名、MACアドレス（取得できる場合）、役割、インストール時刻、使用したGitリビジョン、OSバージョン、結果を表示する。
- イベント履歴とエラー・ログ参照を提供する。
- UIからはISO取得、PXE起動、ディスク初期化などの変更操作を行わない。LAN内公開範囲と読み取り権限も明確にする。

**完了条件:** CLIを使わずc0の準備状況と最後のプロビジョニング結果を把握できる。

## 継続的な検討課題

| 課題 | 当面の方針 |
| --- | --- |
| ワーカーのインストール後の構成変更 | 再構築運用で十分かを観察し、必要になったらAnsible等やNixOS化を比較する |
| 複数台同時インストール | 当面1台ずつ。必要ならMACアドレスに結び付けたシードと並列セッション管理を導入する |
| ノード台帳・再現性 | 実行時Git SHA、ISOハッシュ、生成設定、インストール結果を記録する。c0のローカル専用コミットにも注意する |
| 秘密情報 | 現状は公開SSH鍵のみ。将来トークン等が必要になったら公開HTTP/公開Gitから分離する |
| テスト・障害復旧 | 静的検証の次にQEMUでのインストール検証、ISO取得失敗や再起動を挟む復旧パスを検討する |
| セキュリティ・PXE範囲 | Pixiecore応答対象やHTTP配信範囲を再評価する。再PXEによる意図しない再インストールを避ける |
| バージョンアップ | Ubuntu ISO・Nixpkgs・disko等の更新を手動承認、検証、履歴付きで行う |

## 次の着手順

まずM1を、**ファイル移動だけのPR**、**ISO定義共通化のPR**、**CI追加のPR**のように小さく分ける。M2のCLI設計ではセッション状態・失敗時の動作を先に決め、その後M3の完了通知を加える。M4のWeb UIは状態管理を独自に作り直さず、その読み取りに徹する。

この文書は方針と未着手タスクの記録であり、CLI例や完了検知方式は実装済み機能を表していない。
